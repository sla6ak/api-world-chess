# Логика игрового процесса

## Обзор

Игровой процесс управляется через Colyseus Room `chess_room`. Сервер — **авторитарный**: он принимает ходы от клиентов, валидирует состояние и рассылает обновления обоим игрокам. MongoDB используется для персистентности данных о партиях (начало, ход, завершение).

## Жизненный цикл партии

### 1. Создание комнаты

Когда первый игрок подключается к `chess_room`, Colyseus вызывает `onCreate()`:

- Устанавливается начальное состояние доски (FEN-подобная строка)
- `move: true` (ход белых)
- Все имена игроков и рейтинги пусты
- `result: "pending"`
- `maxClients: 2` (максимум 2 игрока в комнате)

### 2. Подключение игроков (onJoin)

При подключении каждого клиента:

1. `onAuth()` верифицирует JWT токен
2. `onJoin()` назначает сторону:
   - Первый подключившийся → `"wite"` (белые)
   - Второй подключившийся → `"black"` (чёрные)
3. Если оба игрока подключены — создаётся/обновляется запись в MongoDB (`game_db`, коллекция `game`) с `statusGame: "close"`

> **Важно:** Игра стартует автоматически при подключении второго игрока. Событие `gameStart` с данными о соперниках рассылается обоим клиентам сразу после подключения второго игрока.

### 3. Поиск игры (findGame)

Когда оба игрока в комнате, один из них отправляет `"findGame"`:

1. Сохраняются параметры поиска (`typeGame`, `timeControl`, `timePluse`) в состояние комнаты
2. Если игрок ещё не назначен — назначается свободной стороне
3. Если оба игрока назначены и игра ещё не стартовала (`this.gameData` не установлен):
   - Сохраняется игра в MongoDB с полными данными
   - Рассылается событие `gameStart` обоим клиентам
4. Если оба игрока назначены и игра уже стартовала (`this.gameData` уже установлен из `onJoin`):
   - Обновляются параметры поиска в MongoDB
   - Повторная рассылка `gameStart` не происходит
5. Если только один игрок:
   - Отправляется `searching` ожидающему клиенту

### 4. Игровой процесс

Сервер управляет состоянием игры. Клиенты могут запрашивать текущее состояние через событие `startGame`, которое вызывает рассылку `game` события всем подключённым игрокам.

> **Примечание:** Метод `handleGameMove` определён в `ChessRoom.ts`, но **не зарегистрирован** как обработчик `onMessage` — в текущей реализации ходы не обрабатываются на сервере автоматически. Клиентская сторона управляет позицией, а сервер только рассылает текущее состояние по запросу.

Каждое сообщение `game` содержит актуальное состояние доски, стороны, рейтинги и время.

### 5. Завершение игры (gameOver)

Когда один из игроков отправляет `"gameOver"`:

1. Сервер определяет результат для текущего клиента:
   - `"1-0"` и клиент — белые → `"win"`
   - `"0-1"` и клиент — чёрные → `"win"`
   - `"0.5-0.5"` → `"draw"` для обоих
   - Иначе → `"loss"`
2. Сохраняет результат и дату завершения в MongoDB
3. Рассылает `gameOver` обоим клиентам с данными о результате и изменении рейтинга

### 6. Отмена поиска (cancelSearch)

Когда игрок отменяет поиск:

1. Находит и удаляет незапущенную игру из MongoDB (`statusGame: "open"` или `"close"`, `result: "pending"`)
2. Отправляет `search_cancelled` отменившему клиенту
3. Если оппонент в комнате — отправляет `search_cancelled_by_opponent`
4. Закрывает комнату (`this.disconnect()`)

### 7. Отключение игрока (onLeave)

При отключении клиента:

1. Уведомляет оппонента через `mesRes` с `message: "opponent_disconnected"`
2. Если игра не начата (`statusGame: "open"` или `"close"`, `result: "pending"`) — удаляет запись из MongoDB
3. Если игра начата — сохраняет текущее состояние (`position`, `move`) в MongoDB

### 8. Уничтожение комнаты (onDispose)

При уничтожении комнаты (после отключения всех клиентов):

- Если игра завершена (`result !== "pending"`) — финально сохраняет результат в MongoDB

## Состояние игры (Room State)

Состояние хранится **in-memory** в объекте `this.state` Colyseus Room. Оно сериализуется автоматически при каждом broadcast.

### Начальное состояние

```ts
{
  position: ["rnbqkbnrpppppppp88888888888888888888888888888888PPPPPPPPRNBQKBNR"],
  move: true,
  playerWite: "",
  playerBlack: "",
  reitingWite: 800,
  reitingBlack: 800,
  timeWite: 0,
  timeBlack: 0,
  result: "pending",
  idGame: this.roomId,
  typeGame: "standart",
  timeControl: 0,
  timePluse: 0,
}
```

### Позиция на доске

Позиция представлена массивом строк в FEN-подобном формате. Каждая строка — ряд доски (от 8-го ряда к 1-му):

```
[
  "rnbqkbnr",  // 8-й ряд (чёрные фигуры)
  "pppppppp",  // 7-й ряд (чёрные пешки)
  "88888888",  // 6-й ряд (пусто)
  "88888888",  // 5-й ряд (пусто)
  "88888888",  // 4-й ряд (пусто)
  "88888888",  // 3-й ряд (пусто)
  "PPPPPPPP",  // 2-й ряд (белые пешки)
  "RNBQKBNR",  // 1-й ряд (белые фигуры)
]
```

> **Примечание:** В текущей реализации начальная позиция хранится как одна строка в массиве, а не как 8 отдельных строк. Это может быть изменено в будущем.

## Роли и стороны

| Роль Colyseus | Сторона | Описание |
|---------------|---------|----------|
| `"wite"`      | Белые   | Первый подключившийся игрок |
| `"black"`     | Чёрные  | Второй подключившийся игрок |
| `""` (пусто)  | —       | Ещё не назначен |

---

## Результаты партии

| Результат | Значение | Описание |
|-----------|----------|----------|
| `"1-0"`   | Белые выиграли | Белые победили |
| `"0-1"`   | Чёрные выиграли | Чёрные победили |
| `"0.5-0.5"` | Ничья | Партия завершилась вничью |
| `"pending"` | Не завершена | Игра ещё идёт |

## Сохранение в MongoDB

### Когда сохраняется

| Событие | Действие |
|---------|----------|
| REST `POST /game/find` — найден второй игрок | `statusGame` меняется на `"close"`, назначаются `ownerBlack`, `nameBlack`, `reitingBlack` |
| Второй игрок подключается к WS (`onJoin`) | Запись обновляется с данными обоих игроков, рассылается событие `gameStart` обоим клиентам |
| Оба игрока отправляют `findGame` | Обновляются параметры (`typeGame`, `timeControl`, `timePluse`); `gameStart` не рассылается повторно |
| Ход (`game` сообщение) | **Не сохраняется** — только in-memory state |
| `gameOver` | Обновляется `result` и `dateGameOver` |
| `onLeave` (игра не начата) | Запись удаляется |
| `onLeave` (игра начата) | Сохраняются `position` и `move` |
| `onDispose` (результат != pending) | Сохраняется `result` и `dateGameOver` |
| `cancelSearch` | Запись удаляется из MongoDB |

### Статусы игры в MongoDB

| `statusGame` | Описание |
|-------------|----------|
| `"open"`    | Игра создана, ищется второй игрок (REST `createSearchRoom`) |
| `"close"`   | Второй игрок найден (REST) или оба игрока подключились (WS); игра может быть уже запущена или ожидать `findGame` |

## Обработка ошибок

Все обработчики событий в `ChessRoom` обёрнуты в `try/catch` с вызовом `logError()`. Ошибки логируются в файл `logs/errors.log` с временной меткой и контекстом. Сервер не падает при ошибках в обработчиках — клиент получает ошибку через стандартные Colyseus механизмы или не получает ответ.

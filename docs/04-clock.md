# 4. Механика Таймера и Шахматных Часов (Chess Clock Logic)

Архитектура часов — **гибридная**: сервер ведёт авторитетный учёт времени и шлёт тики каждую секунду; клиент между тиками делает собственный быстрый отсчёт (100 мс) для плавности UI и жёстко перезаписывается серверными значениями.

## 4.1 Единицы и контракт

Все временные значения — **секунды** (Number):

| Поле | Смысл |
|---|---|
| `timeControl` | Стартовый запас на партию (60/180/300/...) |
| `timePluse` | Инкремент за каждый свой ход |
| `timeWite` / `timeBlack` | Остаток на часах белых/чёрных |
| `lastMoveTimestamp` | ms-timestamp последнего хода (либо создания часов) |

### legacy-нормализация (минуты → секунды)

Старые записи в БД хранят **минуты**. Во всех точках входа из БД работает эвристика:

```ts
const norm = (v) => { const n = Number(v)||0; return n>0 && n<60 ? n*60 : n; };
```

> 🚨 **Хрупко.** Эвристика неотличима от реального быстрого контроля: режим «30 секунд» (`30s+1s`, уже добавлен в UI) при восстановлении из БД превратится в 30 минут. Тестовый режим сломан по восстановлению. Правильное решение — фиксированная единица + одноразовая миграция БД.

## 4.2 Серверный учёт времени (GameManager)

### Инициализация

`new GameManager({timeControl, timePluse})` → `timers = {white: timeControl, black: timeControl}`; запускается `startClock()` — `setInterval(1000 мс)` на время жизни менеджера.

### Дельта времени (`syncClocks`)

Каждый тик (и перед каждым ходом) вызывается `syncClocks()`:

```ts
const now = Date.now();
const elapsed = Math.floor((now - this.lastTickAt) / 1000);
if (elapsed <= 0) return;
this.lastTickAt = now;
const key = chess.turn() === "w" ? "white" : "black";
timers[key] = Math.max(0, timers[key] - elapsed);
```

Ключевые свойства алгоритма:

- Время вычитается **целыми секундами** (`Math.floor`) — суб-секундная дробь «сгорает» в пользу игрока на каждом тике, но накапливается корректно через `lastTickAt = now`.
- Списывается время со стороны, чей ход **в данный момент** по chess.js (`chess.turn()`), а не по флагу комнаты — источник истины един.
- После каждого успешного хода: `timers[моей стороны] += increment`, `lastTickAt = Date.now()` — отсчёт «переключается» на соперника.
- Падение флага проверяется **только в `syncClocks`**, т.е. на тиках и на входящем ходе.
- Защита **`hasAnyMove`**: флаг не может упасть до первого хода в партии — иначе восстановленная из «битого» снапшота партия (нули в БД) мгновенно завершалась бы таймаутом на старте.

### Тики наружу

```
GameManager.onTick ──▶ ChessRoom.broadcast("timers", {white, black})  // каждую секунду
```

Это главный канал синхронизации: оба клиента ежесекундно получают авторитетные значения.

### Дополнительная жёсткая синхронизация

`timers` также вкладываются в события `move_made` и `gameResumed`, а `timeWite/timeBlack` — в `gameStart`/`game` (через `broadcastState()`).

## 4.3 Клиентская модель (GameArea)

### Хранение

- `clockRef = {white, black}` — ref с дробными секундами (источник для рендера);
- `clockWhite/clockBlack` — React-state, обновляются только при смене **целой** секунды (чтобы не рендерить 10 раз/сек).

### Локальный отсчёт

```ts
setInterval(100 мс):
    key = (gameData.move ? "white" : "black");
    clockRef[key] -= 0.1;
    setClock*(Math.ceil(...)) // только если целая секунда изменилась
```

Тикает только сторона с активным ходом (`gameData.move` из Redux), и только пока `gameEvents.status !== "gameover"`.

### Жёсткая коррекция (устранение пинга)

Три источника перезаписи клиентских часов серверными значениями:

1. `useEffect` по `[gameData.timeWite, gameData.timeBlack, gameData.idGame]` — срабатывает на каждый `timers`-тик, попадающий в Redux (App.tsx → `gameStartSuccess(...{timeWite, timeBlack})`).
2. Обработчик `move_made` в `GameArea` — сразу применяет `msg.timers` (без ожидания Redux-цикла).
3. Обработчик `gameResumed` — восстановленные часы после реконнекта.

Таким образом максимальный дрейф клиента ограничен ~1 секундой (интервал между тиками) — сетевой пинг «перетирается» при каждом апдейте.

## 4.4 Почему возникал баг `00:00` при старте (и что сделано)

Историческая цепочка бага:

1. Старая схема БД имела `timeWite/timeBlack` дефолтом **0** (а в ещё более старых записях — минуты).
2. При создании заявки `createSearchRoom` **не записывал** стартовые часы → в документе оставались 0/мусор.
3. `GameManager.restore()` честно восстанавливал нули → первый же `syncClocks` ронял флаг (мгновенный `timeout` до первого хода), а клиенты видели `00:00` вместо выбранного контроля.

Текущие страховки (все три слоя):

- **Модель:** дефолт `timeWite/timeBlack: 180`, комментарий-контракт «всё в секундах».
- **REST:** `createSearchRoom` явно пишет `timeWite = timeBlack = timeControlSec` при создании.
- **onCreate/onJoin комнаты:** если ходов не было и часы нулевые/«подозрительно малые» — подменяется на полный `timeControl`; `GameManager.restore()` дополнительно считает `≤5% контроля` при нулевой истории артефактом и сбрасывает на полный контроль.

Плюс диагностика: `console.warn` при восстановлении менеджера с неполными часами на партии без ходов.

## 4.5 Известные слабые места таймера

> 🚨 **Отсутствует фоновый воркер таймаутов для оффлайн-партий.** Проверка флага происходит только внутри живого `GameManager`. Если **оба** игрока отключились и комнату выгрузил Colyseus (после `onDispose` GameManager диспозится) — ничей процесс не считает оставшееся время. Партия висит `paused` в БД вечно, рейтинг не пересчитывается. Нужен планировщик (cron/worker), который сканирует `games` с `paused:true` и «дожимает» флаг по сохранённым часам.

> 🚨 **Утечки интервалов застрахованы, но паттерн хрупкий.** `startClock()` начинается с `stopClock()`, `finishGame/dispose` останавливают интервал, `ChessRoom.finalizeAndBroadcast` обнуляет `this.gm`. Однако любой будущий путь создания GameManager вне этих точек (например, второй restore) обязан повторять дисциплину — централизованного гаранта нет.

> ⚠️ **Точность ограничена тиком 1 с + Math.floor.** Суб-секундные потери не учитываются; длительные фризы event loop (GC, блокирующие операции) сдвигают тик, но дельта компенсируется по `Date.now()`, так что накопительной ошибки нет — есть лишь зернистость отображения.

> ⚠️ **`lastMoveTimestamp` ≠ реальному моменту хода при восстановлении.** После `restore()` он инициализируется `Date.now()`; клиентская анимация/рассчёты, полагающиеся на него, получают «обнулённое» время — приемлемо, но стоит держать в уме.

> ⚠️ **Инкремент не ограничен сверху контролем.** Классика Фишера: часы могут расти выше стартового `timeControl` — сейчас так и есть. Если задуман «Капабланка-кап» (cap), его нет.

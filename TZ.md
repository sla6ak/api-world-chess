# Техническое задание: Chess World — Многопользовательская шахматная платформа

## 1. Общее описание

Chess World — веб-приложение для многопользовательских шахматных партий в реальном времени. Платформа состоит из клиентской части (React SPA) и серверной части (Node.js + Colyseus + MongoDB). Приложение обеспечивает авторизацию, поиск соперника, real-time игровой процесс с таймером, сохранение результатов и ведение рейтингов.

## 3. Архитектура взаимодействия клиент-сервер

### 3.1 Авторизация (REST)

Все REST-эндпоинты префиксированы `/auth`:

| Метод | Путь | Описание | Аутентификация |
|-------|------|----------|----------------|
| POST | `/auth/signup` | Регистрация | Нет |
| POST | `/auth/login` | Авторизация | Нет |
| PATCH | `/auth/login/:token` | Подтверждение email | Нет |
| GET | `/auth/current` | Текущий пользователь | Bearer token |
| POST | `/auth/logout` | Выход | Bearer token |
| DELETE | `/auth/delete` | Удаление аккаунта | Bearer token |

JWT-токен действителен 30 дней. Передаётся в заголовке `Authorization: Bearer <token>`.

### 3.2 Игровой процесс (WebSocket)

Подключение к Colyseus-серверу: `ws://<host>:5000/`

Комната: `chess_room`. Клиент подключается через `client.joinOrCreate("chess_room", { token, color })`.

Каждая партия — отдельная Colyseus Room. Room изолирует игроков одной партии.

## 4. Требования к шахматному движку (клиентская сторона)

### 4.1 Отображение доски

- Доска рендерится как сетка 8×8 клеток.
- Каждая клетка — DOM-элемент с CSS-классом `square-light` или `square-dark`.
- Фигуры отображаются как SVG/PNG-элементы внутри клеток.
- Начальная позиция задаётся FEN-подобной строкой: `"rnbqkbnrpppppppp88888888888888888888888888888888PPPPPPPPRNBQKBNR"`.
- Позиция хранится как массив из 64 элементов, каждый элемент — строка: `"r"`, `"n"`, `"b"`, `"q"`, `"k"`, `"p"` (чёрные, строчные), `"R"`, `"N"`, `"B"`, `"Q"`, `"K"`, `"P"` (белые, заглавные), `"8"` (пустая клетка).

### 4.2 Взаимодействие с фигурами

1. **Выбор фигуры** — клик на клетку с фигурой текущего игрока. Фигура подсвечивается классом `selected`.
2. **Отображение допустимых ходов** — после выбора фигуры подсвечиваются клетки, куда можно сделать ход (класс `valid-move`). Для каждой фигуры реализуется свой набор допустимых ходов.
3. **Совершение хода** — клик на подсвеченную клетку перемещает фигуру. Исходная клетка очищается, целевая клетка получает фигуру.
4. **Взятие фигуры** — если целевая клетка содержит фигуру противника, она заменяется.
5. **Переключение хода** — после валидного хода клиент переключает `move` (true → false или false → true) и отправляет обновлённую позицию серверу.

### 4.3 Валидация ходов (клиент)

Клиентская валидация — **предварительная** (UX-цель). Все ходы валидируются сервером.

Правила валидации для каждой фигуры:

| Фигура | Правила движения |
|--------|-----------------|
| Пешка (P/p) | Вперёд на 1 клетку (или 2 с начальной позиции); взятие по диагонали; рокировка не применяется |
| Конь (N/n) | L-образный ход (2+1 или 1+2); может перепрыгивать фигуры |
| Слон (B/b) | По диагонали, произвольное количество клеток; не может перепрыгивать |
| Ладья (R/r) | По вертикали/горизонтали, произвольное количество клеток; не может перепрыгивать |
| Ферзь (Q/q) | Комбинация слона и ладьи |
| Король (K/k) | На 1 клетку в любом направлении; рокировка (короткая/длинная) |

### 4.4 Специальные ходы

- **Рокировка**: при условии, что король и выбранная ладья не двигались, между ними нет фигур, король не находится под шахом, и король не проходит через атакуемые клетки.
- **Взятие на проходе**: доступно в течение одного хода после того, как противник сделал двойный ход пешкой.
- **Промоция**: при достижении последнего ряда пешкой — замена на ферзя, ладью, слона или коня (по выбору игрока).

### 4.5 Обнаружение шаха и мата

- После каждого хода клиент проверяет, находится ли его король под шахом (атакуется ли он фигурой противника).
- Если король под шахом и нет легальных ходов для выхода — мат.
- Если король не под шахом, но легальных ходов нет — пат.
- Клиент отправляет результат серверу через событие с типом `result`.

## 5. Требования к обработке ходов на сервере

### 5.1 Обработка в Colyseus Room

Все ходы обрабатываются в методе `onMessage` комнаты `ChessRoom`:

```
onMessage(client, message) {
  switch (message.event) {
    case "startApp": ...
    case "startGame": ...
    case "game": this.handleGameMove(client, message); break;
    case "result": this.handleGameEnd(client, message); break;
  }
}
```

### 5.2 Валидация хода на сервере

Сервер обязан выполнить **полную валидацию** каждого хода:

1. Проверить, что ход совершает текущий игрок (чей ход `move`).
2. Проверить, что выбранная фигура принадлежит текущему игроку.
3. Проверить, что ход легален согласно правилам шахмат (см. раздел 4.3).
4. Проверить, что ход не оставляет собственного короля под шахом.
5. Если ход некорректен — отклонить, отправить клиенту ошибку.
6. Если ход корректен — применить к состоянию, переключить ход, рассылать обновление обоим игрокам.

### 5.3 Синхронизация состояния

- Состояние игры (позиция, чей ход, результат) хранится **в памяти** сервера в объекте `gameId → gameState`.
- При получении валидного хода сервер обновляет `position` и `move` в памяти.
- Сервер отправляет обновлённое состояние **обоим** подключённым клиентам через Colyseus state synchronization.
- В MongoDB состояние сохраняется **только** при завершении игры или отключении игрока.

### 5.4 Обработка завершения игры

При получении события `result` от одного из игроков:

1. Сервер фиксирует результат: `"1-0"` (белые выиграли), `"0-1"` (чёрные), `"0.5-0.5"` (ничья).
2. Сервер сохраняет финальную позицию и результат в MongoDB (`game_db`).
3. Сервер уведомляет обоих игроков о завершении.
4. Сервер обновляет рейтинг игроков (см. раздел 7).

### 5.5 Обработка отключения игрока

1. При `onLeave` сервер сохраняет текущее состояние в MongoDB.
2. Если оппонент подключён — уведомляет его об отключении соперника.
3. При переподключении — игрок получает текущее состояние из памяти и продолжает игру.
4. Если оппонент недоступен более 15 минут — игра записывается как `"pending"`.

## 6. Требования к таймеру

### 6.1 Архитектура таймера

Таймер — **серверный** (authoritative). Клиент отображает таймер, но сервер управляет временем и синхронизирует его.

### 6.2 Параметры таймера

| Параметр | Описание | Пример |
|----------|----------|--------|
| `timeControl` | Начальное время на игрока (секунды) | 180 (3 минуты), 300 (5 минут) |
| `timePluse` | Добавление времени за каждый ход (секунды) | 0, 2, 5, 10 |

### 6.3 Логика работы

1. При `startGame` сервер устанавливает `timeWite` и `timeBlack` равными `timeControl`.
2. При каждом ходе сервер:
   - Вычитает elapsed time (время с последнего хода) из таймера текущего игрока.
   - Добавляет `timePluse` к таймеру игрока, который только сделал ход.
   - Если таймер игрока ≤ 0 — игра заканчивается, противник побеждает.
3. Сервер передаёт `timeWite` и `timeBlack` в каждом обновлении состояния.
4. Клиент отображает таймер в формате `M:SS`.

### 6.4 Синхронизация таймера

- Сервер отправляет `timeWite` и `timeBlack` с каждым обновлением позиции.
- Клиент **не** считает время самостоятельно — он отображает серверные значения.
- При переподключении клиент получает актуальные значения таймера из памяти сервера.

### 6.5 Отображение на клиенте

Таймер отображается рядом с доской или в верхней части игрового интерфейса:

```
[White: 3:45]  [Chess Board]  [Black: 5:12]
```

Текущий ходящий игрок имеет визуальное выделение (например, подсветка таймера цветом акцента).

## 7. Требования к системе рейтингов

### 7.1 Модель рейтинга

Использовать систему **Elo** (или аналогичную).

| Параметр | Начальное значение | Описание |
|----------|-------------------|----------|
| `currentReiting` | 800 | Текущий рейтинг игрока |
| `maxReiting` | 800 | Максимальный достигнутый рейтинг |

### 7.2 Расчёт рейтинга после партии

Формула Elo:

```
E_A = 1 / (1 + 10^((R_B - R_A) / 400))
E_B = 1 / (1 + 10^((R_A - R_B) / 400))

R_A' = R_A + K * (S_A - E_A)
R_B' = R_B + K * (S_B - E_B)
```

Где:
- `R_A`, `R_B` — текущие рейтинги
- `S_A`, `S_B` — фактический результат (1 = победа, 0.5 = ничья, 0 = поражение)
- `E_A`, `E_B` — ожидаемый результат
- `K` — коэффициент (рекомендуется `K = 32` для новых игроков, `K = 16` для игроков с рейтингом > 2100)

### 7.3 Требования к серверной логике

1. При завершении игры сервер рассчитывает новый рейтинг для обоих игроков.
2. Обновляет поля `currentReiting` и `maxReiting` в коллекции `users` MongoDB (`users_db`).
3. Если `currentReiting > maxReiting` — обновляет `maxReiting`.
4. Результат расчёта сохраняется в документе игры в `game_db`.

### 7.4 Таблица рейтингов (Leaderboard)

**Эндпоинт:** `GET /users/leaderboard`

**Параметры запроса:**
| Параметр | Тип | По умолчанию | Описание |
|----------|-----|-------------|----------|
| `limit` | integer | 100 | Количество записей |
| `offset` | integer | 0 | Смещение для пагинации |

**Ответ (200):**
```json
{
  "leaderboard": [
    {
      "_id": "64a1b2c3d4e5f6a7b8c9d0e1",
      "name": "PlayerName",
      "currentReiting": 1850,
      "maxReiting": 1900,
      "gamesPlayed": 142,
      "wins": 89,
      "losses": 41,
      "draws": 12
    }
  ],
  "total": 1523
}
```

**Требования:**
- Сортировка по `currentReiting` DESC.
- Пагинация с `limit`/`offset`.
- Возвращаются только публичные данные (без email, token).
- Кеширование результатов на 60 секунд.

## 9. Поиск соперника по рейтингу

### 9.1 Алгоритм поиска

При `startGame` сервер выполняет поиск оппонента:

1. Ищет открытые игры (`statusGame: "open"`) с совпадающими параметрами (`typeGame`, `timeControl`, `timePluse`).
2. Среди найденных выбирает оппонента с наиболее близким `currentReiting` к рейтингу запрашивающего игрока.
3. Если оппонент найден — создаётся минимальная запись в MongoDB, `statusGame` меняется на `"close"`, возвращается `opponentId`.
4. Если оппонент не найден — создаётся новая игра в режиме поиска (`statusGame: "open"`), `opponentId = null`.

### 9.2 Критерий «равного рейтинга»

- Диапазон поиска: ±200 рейтинговых очков.
- Если в диапазоне несколько кандидатов — выбирается с наименьшей разницей рейтинга.
- Если в диапазоне нет кандидатов — расширяется до ±400, затем ±600.
- Если оппонент не найден ни в одном диапазоне — игра создаётся в режиме ожидания.

### 9.3 Таймаут поиска

- Если игрок находится в режиме поиска более 60 секунд без оппонента — сервер автоматически начинает игру с AI-противником (фаза 2) или предлагает случайного оппонента вне диапазона рейтинга.

## 10. Требования к фронтенд-реализации

### 10.1 Страница рейтингов

- Эндпоинт `GET /users/leaderboard`.
- Отображение таблицы: ранг, имя, рейтинг, победы/поражения/ничьи, процент побед.

- Эндпоинт `GET /games/history`.
- Список игр с: датой, соперником, результатом, тайм-контролем, типом игры.

- Пагинация.
- Клик на игру → детали (позиция, ходы, результат).

### 10.3 Таймер в игре

- Отображение таймера для обоих игроков в реальном времени.
- Формат `M:SS`.
- Визуальное предупреждение при ≤ 30 секунд (мигание, красный цвет).
- Таймер синхронизируется с сервером при каждом обновлении позиции.

### 10.4 UI/UX требования

- Адаптивный дизайн (mobile-first).
- Поддержка 4 тем (light, dark, chess-classic, ocean).
- Анимации ходов фигур (CSS transitions).
- Звуковые эффекты (опционально): ход, взятие, мат, ничья.
- Toast-уведомления: подключение к комнате, поиск оппонента, результат партии.

## 13. Критерии приёмки

1. Авторизация работает (регистрация, логин, выход, удаление аккаунта).
2. WebSocket-подключение устанавливается и поддерживает reconnection.
3. Поиск оппонента находит игрока в диапазоне ±200 рейтинга.
4. Ходы валидируются на сервере (некорректные ходы отклоняются).
5. Таймер синхронизируется с сервером и отображается корректно.

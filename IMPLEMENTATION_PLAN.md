# План реализации Chess World

## Общая структура

Реализация разбита на **6 фаз**. Каждая фаза содержит шаги с чёткими зависимостями и контрольными точками тестирования. Фазы идут от фундамента к продвинутым функциям.

**Принцип:** каждая фаза завершается тестируемым инкрементом — можно запустить, проверить и подтвердить корректность перед переходом к следующей.

## Фаза 1: Серверная валидация ходов

**Цель:** сервер перестаёт доверять клиенту и валидирует каждый ход.

### Шаг 1.1 — Создать модуль валидации ходов (backend)

  - Слон: диагональ, произвольное расстояние, без перепрыгивания
  - Ладья: вертикаль/горизонталь, произвольное расстояние, без перепрыгивания
  - Ферзь: комбинация слона и ладьи
  - Король: на 1 клетку в любом направлении
  - Рокировка: проверка, что король и ладья не двигались, путь свободен, король не под шахом, не проходит через атакуемые клетки
- [ ] Реализовать функцию `isSquareAttacked(board, square, byColor)` — проверка, атакуется ли клетка фигурами указанного цвета

- [ ] Реализовать функцию `hasLegalMoves(board, color)` — проверка, есть ли у игрока хотя бы один легальный ход (для определения мата/пата)

## Фаза 3: Система рейтингов (Elo)

**Цель:** после завершения игры рейтинги игроков обновляются.

### Шаг 3.1 — Реализовать Elo-расчёт (backend)
- [ ] Создать `src/helpers/eloCalculator.js`:
  - Функция `calculateElo(ratingA, ratingB, result)` → `{ newRatingA, newRatingB }`
  - `E_A = 1 / (1 + 10^((R_B - R_A) / 400))`
  - `E_B = 1 / (1 + 10^((R_A - R_B) / 400))`
  - `K = 32` (для всех игроков на данном этапе)
  - `R_A' = R_A + K * (S_A - E_A)`
  - `R_B' = R_B + K * (S_B - E_B)`
  - `S_A`, `S_B`: 1 (победа), 0.5 (ничья), 0 (поражение)
- [ ] Округлить результат до целого числа

### Шаг 3.2 — Интегрировать Elo в обработку результата

  3. Обновить `currentReiting` и `maxReiting` в `users_db`
  4. Сохранить `reitingWite`, `reitingBlack` (до) и `reitingWiteNew`, `reitingBlackNew` (после) в документе игры в `game_db`

## Фаза 4: Поиск соперника по рейтингу

**Цель:** при поиске оппонента система выбирает игрока с ближайшим рейтингом.

### Шаг 4.1 — Реализовать алгоритм поиска (backend)
- [ ] Создать `src/helpers/matchmaking.js`:
  - Функция `findOpponent(userId, currentRating, typeGame, timeControl, timePluse)`
  - Алгоритм:
    1. Искать открытые игры (`statusGame: "open"`) с совпадающими параметрами
    2. Искать среди них игроков с `|opponentRating - currentRating| ≤ 200`
    3. Выбрать с наименьшей разницей рейтинга
    4. Если нет в диапазоне ±200 — расширить до ±400
    5. Если нет в диапазоне ±400 — расширить до ±600
    6. Если всё ещё нет — вернуть `null` (создать новую комнату в режиме ожидания)

- [ ] По истечении 60 секунд, если оппонент не найден:

  - Или создать AI-противник (фаза 5)

### Шаг 4.3 — Фронтенд: индикатор поиска

### Контрольная точка 4

**Тестирование:**

## Диаграмма зависимостей

```
Фаза 0 (Baseline)
  │
  ▼
Фаза 1 (Валидация ходов)
  │
  ├──→ Фаза 2 (Таймер) ── зависит от: Фаза 1 (обработка ходов)
  │       │
  │       ▼
  │     Фаза 3 (Рейтинги) ── зависит от: Фаза 1 (результат игры), Фаза 2 (таймер)
  │       │
  │       ├──→ Фаза 4 (Поиск соперника) ── зависит от: Фаза 3 (рейтинги)
  │       │
  │       ▼
  │     Фаза 5 (UI/UX) ── зависит от: Фаза 3 (leaderboard, history), Фаза 4 (поиск)
  │       │
  │       ▼
  │     Фаза 6 (Тестирование + деплой) ── зависит от: всех фаз
```

## Параллельные потоки

Можно выполнять параллельно:
- **Фаза 1 + Фаза 5 (частично):** вёрстка таймера и страниц рейтингов/истории можно делать параллельно с бэкенд-валидацией
- **Фаза 3 + Фаза 4:** Elo-расчёт и matchmaking можно разрабатывать одновременно
- **Фаза 5 (UI):** все фронтенд-страницы можно делать параллельно
